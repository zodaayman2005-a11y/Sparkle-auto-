# Sparkle Auto — Quality Gates
Authored adapter to master-plan §14 and the supplied visual-director QA modules.
Use visual-qa-refinement for diagnosis; use this page-specific acceptance scope.
Read `references/INSTALL-SMOKE-TESTS.md` only for installation validation.

## Installation is a separate gate
File count, frontmatter, checksums and references can pass without a website existing.
Verify actual skill discovery separately. Never imply that an installed image workflow
grants access to an image generator or that installer tests prove design quality.

## Actual website review after implementation is authorized
Check ar and en at widths 320, 360, 390, 768, 1024 and 1440; inspect overflow/reflow
at each and actual representative full-page and close-up screenshots. Also check a
short-height window, text zoom, keyboard input and changing reduced-motion preferences.
Fix content/font/viewport/state when comparing captures; open the screenshots yourself.

## Hard gates
Scope/permissions; product and commercial truth; semantic web controls; authentic proof;
readable text/contrast/focus; keyboard/forms/dialog; responsive locales; stable motion
alternatives; honest asset provenance; measured delivery and explicit missing checks.
A visual score cannot compensate for a false claim, broken CTA or unreachable chapter.

## Required interaction coverage
Header links and mobile drawer; language switch; chapter jump/bypass; rapid and reverse
scroll; zero/one/many chapter edge cases; media missing/ready/error; Escape/close/focus;
video stop and scroll restoration; FAQ; form validation, loading, success, error and retry.
Check image failure, listener cleanup, semantic reading order and no JS-gated main copy.

## Visual gate
White/blue identity, deliberate section rhythm, large readable authentic product proof,
strong but clear type, no decorative clutter, no tiny whole-dashboard proof on mobile.
Use the existing source rubric as a heuristic with observations. Do not invent scores.
Match the proposed fonts and props to the actual composition before scaling production.

## Tool and performance evidence
Use the real project's lint/typecheck/build/test commands. Run available browser and
accessibility tools; supplement automation with relevant manual checks. Record actual
commands, routes, viewport/locale, outputs and screenshot paths that exist.
Separate lab measurements from field Core Web Vitals. No autoplay hero download or
eager fetching of twelve videos. Do not label a local score as a field conversion gain.

## Defect loop
Classify the failure as source truth, concept, asset, layout/code, interaction or delivery.
Repair the smallest relevant layer; repeat the same check. Do not regenerate art for
CSS overflow. Reuse accepted work and preserve actual user modifications.

## Honest status and release
Use passed/failed/not_run/blocked/not_applicable with a reason. Separate implemented,
integrated, qa_passed, agent_selected, user_approved and released.
No browser access → mark browser gates not_run, not fully responsive tested.
Close critical/major issues or report them plainly. Publishing needs separate permission.
